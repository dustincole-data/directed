## 1. Purpose

A gallery that shows, element by element, the difference between what Claude Code produces **by default** and what it produces when a specific skill, prompt pattern, or tool is applied on top. Every cell is generated by actually running the method it claims to demonstrate.

Two goals, both first-class:

1. **Decide the dustincoledata graphic house style** by seeing real options for every element instead of guessing from references.
2. **Publish** the gallery plus an article so others can see their concrete options for getting good visual output out of Claude Code.

### Non-goals

- Not a charting library. Not a reusable component kit for other people.
- Not a benchmark or a research paper. Showcase rigor with honest footnotes (§9).
- Not a claim that any arm is universally better. The gallery presents options; the reader decides.

## 2. Naming

Working name **Directed** — from the brand anchor: Dustin directs AI to build real visual things and verifies them. The gallery is literally default output vs. directed output.

Subdomain: `directed.dustincoledata.com`. Alternates if it doesn't land: `Default → Directed`, `House Style`, `Baseline`.

## 3. Core concept: the cell

A **cell** is one (element row × arm) pair — a single small rendered example plus its full provenance.

A **row** is one element of a data visualization (e.g. "typeface", "diverging palette", "per-datum gradient marks").

An **arm** is how that cell was produced:

| Arm | Name | How it is produced |
|---|---|---|
| **A** | default | Clean subagent. Prompt contains only the dataset and a naive ask. No CLAUDE.md, no skills, no research in context. |
| **B** | skill | A real installed skill actually invoked — `/impeccable <cmd>`, the bundled `dataviz` skill, `intent:*`, or the project's own craft-as-code skill. |
| **C** | tool | A real external tool loop actually run — reference-PNG + Chrome screenshot-diff, Figma MCP, or an image model generating the target mock. |

Not every row has all three arms. Rows declare their arms explicitly (§6).

### 3.1 Refine vs from-scratch (the isolation rule)

Each row declares one of two modes, and the mode is printed on the cell page:

- **refine** — Arms B and C run **on Arm A's output**. This isolates the lever: the only difference between A and B is the skill's edit. Used for typography, color, spacing, annotation, polish.
- **from-scratch** — Arms B and C generate **independently** from the same brief. Used where the lever *is* the generation decision: library choice, radial vs cartesian, custom glyph design, reference-image conformance.

Mixing these silently would make the gallery dishonest. Declaring it per row is the fix.

### 3.2 Immutability

Generated code is **immutable**, following the same rule as the Brain vault's `raw/`. Once a cell is generated it is never hand-edited. If a cell is wrong, a new version is generated (`-v2`) and the old one stays. Hand-polishing a baseline — or a treated cell — silently converts the gallery from evidence into decoration.

The **only** permitted post-generation edits, applied uniformly to every arm and disclosed on `/method`:

1. Injecting the shared dataset import.
2. Injecting the shared mount point / container id.
3. Removing a hardcoded page background that would fight the gallery shell.

Anything else is a regeneration.

### 3.3 Cell on disk

```
cells/<family>-<nn>-<slug>/
  <arm>/
    cell.json      # manifest, see below
    chart.js       # generated code, unedited
    render.svg     # frozen render (PNG only if the technique requires raster)
```

`cell.json`:

```json
{
  "id": "color-03-diverging.B",
  "family": "color",
  "row": "color-03-diverging",
  "rowTitle": "Diverging scale / spectral within poles",
  "arm": "B",
  "mode": "refine",
  "method": { "kind": "skill", "name": "dataviz", "args": "", "ranOn": "color-03-diverging.A" },
  "prompt": "<verbatim prompt text, exactly as sent>",
  "fixture": "table12",
  "generated": "2026-07-25",
  "runs": 3,
  "shipped": "median",
  "notes": ""
}
```

`prompt` is verbatim and non-negotiable — it is what makes the comparison checkable by a reader.

`runs`/`shipped` apply to **Arm A only**, where run-to-run variance is the thing being managed (§9). Arms B and C are single deterministic invocations of a named skill or tool: `runs: 1`, `shipped: "only"`. Generating three directed attempts and picking the prettiest would be exactly the cherry-picking the gallery exists to avoid.

## 4. Architecture

Astro static site, matching the pattern of the existing dustincoledata project sites (Namesake, Cascade, Illusions, Meaning Map, Where America Moves, Real Price, By Example). Astro 5 / Node 22, self-hosted fonts, no external CDN.

```
src/
  fixtures/          # the three frozen datasets (§5), plus type definitions
  craft/             # verified craft-as-code wirings (§7) — the durable artifact
  components/
    Swatch.astro     # one cell: render + arm label + method chip
    RowStrip.astro   # one row: A | B | C side by side, mode badge, pin toggles
    Provenance.astro # verbatim prompt, method, code diff vs arm A
  pages/
    index.astro      # swatch grid, grouped by family
    build.astro      # 14-stage hero build
    cell/[id].astro  # provenance page per cell
    mine.astro       # pinned picks -> exported house-style tokens
    method.astro     # methodology, caveats, refuted list, gaps
cells/               # generated cells, immutable (§3.3)
scripts/
  render-cell.mjs    # headless render of a cell's chart.js -> render.svg
  build-registry.mjs # cells/**/cell.json -> src/generated/registry.json
  verify-cells.mjs   # integrity gate (§8)
```

### 4.1 Data flow

```
fixtures (frozen)
   |
   v
cell factory (subagent / skill run / tool loop)  --writes-->  cells/<row>/<arm>/{cell.json, chart.js}
   |
   v
render-cell.mjs  --writes-->  cells/<row>/<arm>/render.svg
   |
   v
build-registry.mjs  --writes-->  src/generated/registry.json
   |
   v
Astro build --> static site (grid / build / cell / mine / method)
```

The site build **never** executes generated chart code at request time. Cells are pre-rendered to SVG and the SVG is inlined. This keeps the site static, fast, CSP-clean, and immune to a generated cell throwing at build time.

### 4.2 Component boundaries

- `Swatch` — given a cell id, renders the frozen SVG at a fixed box with the arm label and method chip. Knows nothing about rows or families.
- `RowStrip` — given a row id, lays out its arms in declaration order with the mode badge. Knows nothing about how cells were generated.
- `Provenance` — given a cell id, renders prompt, method, and diff. Pure display.
- `registry.json` — the single interface between the generation pipeline and the site. The site reads only this; the pipeline writes only this.

This means the gallery shell can be redesigned without touching a single cell, and cells can be regenerated without touching the shell.

## 5. Fixtures

Three frozen datasets, committed as static JSON, never regenerated. Every cell in a family uses the fixture that family declares.

| Fixture | Shape | Serves | Proposed source |
|---|---|---|---|
| `table12` | 12 rows: label, value, delta-vs-baseline | type, color, axes, layout, annotation, legend, numbers, medium | Lichess opening win-rates (12 openings, win % and delta vs the 50% baseline) — CC0 open database, gives a real diverging baseline. Fallback: World Bank life expectancy, 12 countries, delta vs world mean. |
| `hero8` | 8 rows: label, size, distance, colour | mark craft (custom glyphs, per-datum gradients, halo, texture) | The 8 planets. Deliberate parity with the Visual Cinnamon technique's own N; publicly known values; no licensing. |
| `cycle12` | 12 ordered points, periodic | radial / non-cartesian layouts, motion | Monthly mean daylight hours at a fixed latitude — pure astronomical formula, zero sourcing, perfectly cyclical, and does not overlap Climate Fingerprint. |

**Deliberately avoided:** baby names (Namesake), state migration (Where America Moves), climate normals (Climate Fingerprint), occupations (Meaning Map), prices (Real Price), college sports (Fanbase Weather). Reusing them would make this read as a remix of existing projects.

Fixtures are the one item flagged for veto at spec review.

## 7. Craft-as-code module (`src/craft/`)

Only the wirings that survived 3-vote verification. Each exports a small, documented function and is used by Arm B/C cells.

| Export | Technique | Source |
|---|---|---|
| `perDatumRadialGradient()` | One `radialGradient` per datum joined over `<defs>`, id derived from the datum, highlight off-centre (cx/cy 25–35 %, r 60–65 %), stops brightened/darkened from that row's own colour. Off-centre placement is what produces the sphere read; centred gives a bullseye. | Visual Cinnamon, data-based SVG gradient; Observable hexagon playground |
| `spectralField()` | `gradientUnits="userSpaceOnUse"` with `x1`/`x2` at the layout extent so all marks sample one continuous multi-stop ramp instead of restarting per bounding box. Ships the verified 10-stop blue→red ramp. | Observable hexagon playground; W3C SVG 1.1 pservers; MDN gradientUnits |
| `annotationAdjacency()` | Place annotation text on or beside its mark; short uncrossed leaders only when adjacency is impossible; legend last. Critical labels pinned, secondary text offloaded to tooltip. | arXiv 2604.07691v1 practitioner interview study |

**Excluded on purpose:** the glow / halo filter recipe. It was voted down 3-0 in verification. It gets `mark-04-glow` as a visible gap row rather than a fabricated cell. Texture and legend-as-art are similarly flagged as needing sourcing before their Arm B can be honestly built.

Each export carries its perf ceiling in a doc comment: N marks = N gradient defs is fine at tens, a hazard past hundreds.

## 8. Integrity gate (`scripts/verify-cells.mjs`)

Runs in CI and pre-commit. A cell that fails any check does not ship.

1. Every cell directory has `cell.json`, `chart.js`, `render.svg`.
2. `cell.json.prompt` is non-empty and contains no placeholder text.
3. Every row declares `mode` and at least one arm; declared arms all exist on disk.
4. `mode: refine` cells in arms B/C name a `method.ranOn` that resolves to an existing arm-A cell.
5. Every cell names a fixture that exists in `src/fixtures/`.
6. `chart.js` hash matches the hash recorded at generation time — proves no hand-editing after the fact.
7. Gap rows (`mark-04-glow`, `legend-03-art`, `mark-05-texture`) carry a `gap` field with a reason, and the site renders the gap panel rather than an empty slot.

Check 6 is what makes §3.2 enforceable rather than aspirational.

## 9. Methodology and honesty (`/method`)

Stated plainly on the page, not buried:

- **Arm A varies between runs.** Three generations per default cell; the median-looking one ships; `runs` and `shipped` are recorded in every manifest. One generation is not "the default."
- **Contamination is never zero.** Control subagents share the same model weights and system prompt as the directed arms. They are naive in *context*, not in *training*.
- **The permitted post-generation edits** (§3.2) listed exactly.
- **Refine vs from-scratch** per row, with why the isolation matters.
- **Gaps published as gaps.** Glow, texture, legend-as-art are unsourced. Shown as unanswered rather than filled with a guess.
- **Refuted claims section.** The nine claims that failed verification during research, listed so no reader picks them up secondhand: the glow filter recipe, the "3 annotations max 5" budget, D3 line-count figures, the 175-chart defect statistics, "conversational refinement mostly fails", "vocabulary is the binding constraint", "models cannot judge aesthetics", "9 of 10 export to Illustrator", "the annotation layer defines editorial graphics."
- **Vendor-doc dependency.** The Anthropic-documented levers were read at a specific version; docs churn. Date-stamped.
- **This is not a benchmark.** No scores, no winner declared per row.

## 10. `/mine` — the house-style output

Any cell can be pinned. `/mine` collects pins and emits a token file:

```
tokens.css     # --font-*, --color-*, --space-*, mark treatment flags
house-style.md # prose summary of the picks with links back to source cells
```

LocalStorage only, no backend, no accounts. Export is a download. This is the artifact that ends the "what should my graphics look like" question with evidence instead of taste-by-assertion.

## 11. `/build` — the hero build

One chart on `table12`, 14 stages, scroll-driven, each stage adding exactly one lever. Every stage links to the row that isolates that lever.

```
 0  bare Claude, naive prompt, whatever library it picks
 1  + library change (raw D3/SVG)
 2  + /impeccable typeset
 3  + designed palette
 4  + accent/neutral discipline
 5  + axis distillation
 6  + baseline and units honesty
 7  + sort order
 8  + custom glyph
 9  + per-datum gradient marks
10  + spectral field across marks
11  + annotation adjacency
12  + legend removed, labels pinned
13  + reference-PNG screenshot-diff conformance pass
```

Stages are cumulative, so `/build` deliberately entangles levers — that is why the swatch grid exists alongside it.

## 12. Phasing

### Phase 1 — machinery + 9 rows (~24 cells)

Rows: `type-01-typeface`, `type-02-scale`, `type-04-numerals`, `color-01-categorical`, `color-03-diverging`, `color-06-accent`, `mark-01-glyph`, `mark-02-gradient`, `mark-07-overlap`.

Chosen so Phase 1 exercises both modes (`mark-01` is from-scratch), the craft module (`mark-02`), a validator skill (`color-03`), and three different Arm-B skills.

Deliverables: fixtures, cell factory, `render-cell`, `build-registry`, `verify-cells`, `Swatch`, `RowStrip`, `Provenance`, `/` and `/cell/<id>`, `src/craft/` with all three wirings.

**Gate: Dustin reviews the look before Phase 2 generates 70 more cells.**

### Phase 2 — remaining 39 rows (83 cells)

Mass production through proven machinery. `/method` and `/mine` land here. Texture and legend-as-art get a research pass first; if they stay unsourced they ship as gap rows.

### Phase 3 — hero build + article

`/build`, then the article via `/write-blog`, then the project card on dustincoledata.com/projects.

## 13. Risks

| Risk | Mitigation |
|---|---|
| 107 cells is a lot of generation | Phase 1 gate at 24 cells; kill cheap if the format doesn't land |
| Arm A run-to-run variance reads as cherry-picking | 3 runs, median ships, disclosed per cell in the manifest. Arms B/C run once — see §3.3 |
| A skill's Arm B is barely different from Arm A | Publish it anyway. A null result is a real finding and protects credibility |
| Skill auto-activation is unreliable (~coin-flip per community reports) | Arm B always invokes the skill **explicitly** by name, never relies on auto-match. Recorded in the manifest |
| Immutability gets quietly violated to make a cell look better | Hash check in `verify-cells.mjs` (§8 check 6), enforced in CI |
| Vercel push ≠ autodeploy on some of the existing sites | Deploy step confirms with `npx vercel --prod --yes` if the GitHub hook doesn't fire |
| Gap rows look like unfinished work | `/method` frames them as published gaps; each gap panel states what is missing and what would close it |
